## devlog

### 🔴 high — re-encoded output can exceed the `max` character limit, causing Telegram to reject the message

`src/telegram.js:10` · commit `9050663`

`plain.slice(0, max - 1)` is measured on the *decoded, tag-stripped* string, but the return value is built by re-encoding `<` → `&lt;` (3 extra chars) and `>` → `&gt;` (3 extra chars). Any decoded `<`/`>` characters that fall within the slice are re-encoded in the output, expanding it beyond `max`; Telegram enforces a hard character limit and will return `"Bad Request: message is too long"`, making the bot silently fail to send. Fix: apply the slice *after* re-encoding (or over-slice by enough headroom to absorb worst-case expansion, e.g. `plain.slice(0, max - 1 - headroom)`), then append `…`.

### 🟡 low — incomplete entity decode leaves unrecognised entities double-encoded in the plain-text fallback

`src/telegram.js:10` · commit `9050663`

The entity decode step only handles `&lt;`, `&gt;`, `&quot;`, `&amp;`; numeric references (`&#8212;`) and other named entities (`&nbsp;`, `&apos;`, `&hellip;`, etc.) survive into `plain` as literal `&…;` strings, then have their `&` escaped to `&amp;`, producing garbage like `&amp;nbsp;` or `&amp;#8212;` in the sent message. Fix: extend the decode regex to cover at least numeric references and the named entities actually used in the HTML this function receives, or use a small existing HTML-entity decode library.

## dispecink

### 🟠 medium — `paperclip_runs()` blocks the `awake` mutex for up to 4 s each tick

`src-tauri/src/awake.rs:413` · commit `ad78719`

`paperclip_runs()` is called inside `with(|i| tick(…))`, which holds the shared `STATE` mutex for the entire tick. The function makes up to `1 + N` synchronous `curl` calls (one for `/companies`, one per company), each with a 2-second timeout. With two companies and both timing out, the lock is held for up to 4 seconds — longer than the 5-second tick interval. Every other Tauri command handler that calls `with()` (status queries, sleep/wake commands, page heartbeats — at least 8 other call sites) will block for that entire window, stalling the UI or causing the page's 60-second freshness window to lapse incorrectly.

**Fix:** extract `paperclip_runs()` outside `with()` — call it before acquiring the lock, then pass the result into `tick()` as a parameter, so the mutex is held only for the CPU-bound decision logic.

### 🟡 low — Guard's `GUARD_SINCE` store is cleared even when only some agents came back

`src/main.ts:262` · commit `810f1cc`

After waking agents, `localStorage.removeItem(GUARD_SINCE)` removes the entire per-agent timestamp map unconditionally. If `back` is a strict subset of `paused` (one agent was manually un-paused in the meantime and is already `running`), the timestamps for the remaining still-paused agents are wiped. The next run of `guardClaude` on the next tick will find `paused.length > 0` but `since` empty, so when those agents eventually do get resumed, `unstrand()` is never called and their stranded Paperclip tasks are never recovered.

**Fix:** instead of removing the whole key, delete only the entries for agents in `back`: `for (const a of back) delete since[a.id];` and then either write back the pruned object or remove the key only when it becomes empty.

## job-tracker

### 🟠 medium — `chat()` client created per `scoreFit` call; "stay on Workers AI" stickiness lost between the two scoring tiers

`server/scout/score.ts:48` · commit `2a4d8e1`

`scoreFit` calls `chat(env, tier)(…)` — constructing a brand-new client each time. The stickiness that prevents hopping back from Workers AI to Gemini (`onWorkers` flag) lives inside the closure returned by `chat()`, so it is discarded when the call returns. In `tick.ts:354–364`, the cheap call runs first; if it had to fall back to Workers AI, the precise follow-up call (line 364) starts a fresh client and tries Gemini again from the top — exactly the cross-provider tool-history mixing the comment on line 8 of `chat.ts` warns is broken ("Gemini 3 rejects tool-call history it did not produce itself"). For scoring this doesn't cause a tool-history problem (no tool calls), but the intent of the design is violated and any future caller that does carry history will silently get a bad response instead of an error. Fix: lift the `chat()` client creation out of `scoreFit` (pass the `ask` function in, or create it once in `score` in `tick.ts` and reuse it for both tiers).

### 🟡 low — `JSON.parse(out.content ?? 'null')` silently swallows a parse error, scoring a posting as 0

`server/scout/score.ts:57` · commit `2a4d8e1`

If the model returns malformed JSON, `JSON.parse` throws a `SyntaxError` that propagates uncaught out of `scoreFit`; the caller in `tick.ts` has no `try/catch` around it either, so the whole `score()` function rejects and the posting is left in whatever state it was in (no status update, no error message stored). The defensive cast to `null` only applies when `out.content` is `null`, not when the string is unparseable. Fix: wrap the `JSON.parse` in a `try/catch` and throw a descriptive `Error` (or return a sentinel) so the outer error handling in `tick.ts` can store a human-readable status on the suggestion row.

### 🟠 medium — Raw HTTP/1.1 fetch doesn't handle chunked transfer encoding
`src-tauri/src/wisp.rs:40-48` · commit `757df57`

`read_to_string` reads until the server closes the connection and then `split_once("\r\n\r\n")` takes everything after the headers as the body. If Wisp responds with `Transfer-Encoding: chunked` (common with HTTP/1.1 keep-alive or frameworks that stream), the "body" will be the raw chunked wire format — chunk-size lines mixed into the JSON — making `serde_json::from_str` silently return `None` on every call, so the buddy never reacts to Wisp. Either send `HTTP/1.0` in the request line (servers typically reply with a plain body), or use `reqwest` here as well.

### 🟠 medium — Config read-modify-write race between the reminder thread and the tray
`src-tauri/src/config.rs:49-55` · commit `1962d96`

`set_field` does a full `config_load → mutate → config_save` cycle without any lock. The reminder thread calls `store → set_field` every 5 s; the tray can call `set_field` concurrently for the bedtime or motion-switch fields. Two concurrent calls can both read the same snapshot, each overwrite a different key, and the second write silently discards the first key's change — e.g. a reminder is written but the bedtime the user just set is lost. Protect the read-modify-write with a `Mutex<()>` in the config module.

### 🟡 low — Reminder IDs are not unique if two reminders are added within the same millisecond
`src-tauri/src/reminders.rs:97-98` · commit `1962d96`

`new_id()` is `now_ms() XOR (pid << 20)` — identical within the same millisecond from the same process, which can happen when the model calls `set_reminder` twice in one tool-call round-trip. Duplicate IDs mean `reminder_remove` will silently delete both reminders when the user cancels one. Add a per-process monotonic counter: `format!("{:x}", now_ms() ^ ((COUNTER.fetch_add(1, Ordering::Relaxed) as i64) << 20))`.
