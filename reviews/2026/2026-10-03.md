## devlog

### 🔴 high — `fitLines` silently drops entire message when no newline exists before the limit
`src/telegram.js:6–7` · commit `7486a15`

When the HTML contains no `\n` in the first 3,998 characters (e.g. a single very long line, or a first line longer than 4,000 chars), `lastIndexOf('\n', max - 2)` returns `-1`, `Math.max(-1, 0)` resolves to `0`, and the returned string is just `"\n…"` — every character of the message is lost and Telegram receives an empty-looking notification. Fix: when `cut === -1`, fall back to a hard character-level slice at `max - 1` instead of slicing from 0:

```js
const cut = html.lastIndexOf('\n', max - 2);
return cut > 0
  ? `${html.slice(0, cut)}\n…`
  : `${html.slice(0, max - 1)}…`;
```

## dispecink

### 🟠 medium — `GUARD_SINCE` not updated when a second wave of agents is paused
`src/main.ts:225` · commit `fa669b9`

`GUARD_SINCE` is recorded only when `!paused.length` — i.e. the very first time the guard pauses any agent. If a running agent finishes its run and gets paused on a later tick (the soft-pause path at 90–97 %), `paused` is already non-empty, so the timestamp is not updated. When the limit resets, `unstrand` uses the original (earlier) timestamp, potentially moving tasks that were blocked *before* the pause of that second agent — tasks Paperclip blocked for an unrelated reason — back to `todo` or `in_review` incorrectly. Fix: record `GUARD_SINCE` whenever `now.length > 0` unconditionally, or take the minimum of the existing and the new timestamp so it always covers the full pause window.

### 🟡 low — Paperclip watchdog `paperclipDown` counter not reset after a successful slow-probe
`src/main.ts:350–357` · commit `f7db2b0`

After the 30 s health probe returns `alive = true` the function returns early without resetting `paperclipDown`. On the next snapshot tick Paperclip is still offline in the snapshot (the slow response hasn't landed yet), so `paperclipDown` increments again and a new probe starts immediately, wasting a Tauri `invoke` and another 30 s thread, potentially overlapping if the first probe is still in flight (the `paperclipProbing` guard prevents that, but the intent is to wait before retrying). Fix: set `paperclipDown = 0` (or `= 1`) when `alive` is true so the check resets to a clean baseline before the next offline streak counts up again.

## gemini-jobs

### 🔴 high — `tail` length comparison is wrong; the truncation notice never fires

`run.sh:29` · commit `d852979`

`tail` is the **sliced list** (up to 100 items), while `len(lines)` is the total. The guard `if len(lines) > len(tail)` is correct in intent, but `tail` was **already built with the line-length cap** (`l[:500]`), so its length equals `min(len(lines), 100)`. When `len(lines) == 100` the condition is `100 > 100` → `False`, and the omission notice is silently skipped even though every line may have been truncated to 500 chars. More critically, if `lines` is empty, `lines[-100:]` is `[]`, the `or ["(nic)"]` branch fires, and then `len(lines) > len(tail)` is `0 > 1` → `False`, so `tail` stays as `["(nic)"]` — correct by accident, but the empty-input path was not considered. The notice condition should compare against the **original** line count before slicing: capture `total = len(lines)` before building `tail`, then use `if total > len(tail)`.

### 🟠 medium — `open(sys.argv[2], "w")` is never closed; on a crash mid-write the final report can be incomplete or empty

`run.sh:32` · commit `d852979`

The Python snippet writes the final report with a bare `open(...).write(...)` call — no `with` block, no explicit `close()`. CPython will close it at GC time, which is typically fine, but if the process is killed mid-write (e.g. by the OS OOM killer) the OS buffer may not be flushed, leaving an empty or truncated `$report` that is then POSTed verbatim to Paperclip. Fix: wrap in `with open(sys.argv[2], "w") as f: f.write(...)` to guarantee a flush+close before the script exits.

## hlidaci

### 🟠 medium — Silent scan still leaves the plan file unreadable on write error

`uklid.py:77` · commit `249b658`

`json.dump(…, open(PLAN, "w"), …)` opens the plan file for writing but the file handle is never closed — it relies on CPython's reference-counting GC to flush and close it. On any Python implementation that doesn't guarantee immediate collection (PyPy, or under memory pressure in CPython), the file may be empty or partially written when `apply()` immediately reads it back at line 91. The same pattern also exists at line 85 (`STATE`) and line 121. Fix by wrapping every `open()` used for writing in a `with` statement so the file is guaranteed flushed and closed before any subsequent read.

### 🟡 low — Stale-plan refresh silently resets the quiet period when disk usage is below the threshold

`uklid.py:80–85` · commit `249b658`

The intent of `silent=True` is explicitly to *not* start the quiet period. However, `scan()` reads `STATE` and evaluates the notify condition on every call — the `state["notified"]` timestamp is only written when the notify branch is taken, which is already gated by `not silent`. So the quiet period is correctly not updated. **But** if the disk happens to be under `NOTIFY_GB` at refresh time (`silent=True`), and then the user triggers a normal `scan()` before the next nightly run, the normal scan will fire the notification immediately (the quiet period has not been touched). This is the correct behaviour, but the comment at line 94–95 ("does not start the quiet period") implies the opposite intent for that case — no code change needed, but the comment is misleading and could confuse a future maintainer. Clarify the comment to say the quiet period is left unchanged regardless of disk size.

## job-mail

### 🟠 medium — `parseModelArray` returning `[]` propagates silently into `index.js` action loop

`src/index.js:113` · commit `96ae41f`

`index.js` calls `parseModelArray` and iterates the result to decide which emails to act on (add to board, send Telegram messages, etc.). When the model returns malformed JSON the function now logs to `stderr` and returns `[]`, which silently skips *all* mails in that run — indistinguishable from a day with no relevant mail and with no alert to the user. The commit message itself notes this risk ("an empty digest looks exactly like a day with no mail"), but only `sweep.js` is observable via the Telegram sweep report; `index.js` runs as a cron and its `stderr` is only visible in logs that the developer must actively check. Fix: in `index.js`, after the `parseModelArray` call, check if the returned array is empty *and* the raw model output is non-empty, and if so throw (or at minimum send a Telegram alert) so the failure is surfaced the same way other run errors are.

### 🟡 low — `Hromadná` status `.catch` fallback is missing `uidNext`, making `lastUid` silently `NaN` if the fallback were ever truthy

`src/sweep.js:31–32` · commit `9379d83`

The `.catch(() => ({ messages: 0 }))` fallback object omits `uidValidity` and `uidNext`. Currently this is safe only because `messages: 0` is falsy so the button is never built. If a future change alters the guard condition or the fallback value, `hromadna.uidNext - 1` would silently evaluate to `NaN`, the button payload would carry `lastUid: NaN`, and `client.search({ uid: '1:NaN' })` would produce an undefined IMAP result or throw.
